# Model Card — Appliance Energy Forecaster

## Overview

| | |
|---|---|
| **Task** | Univariate target, multivariate inputs; one-step-ahead regression |
| **Target** | `Appliances`, household appliance energy consumption, in Wh |
| **Horizon** | 1 step = 10 minutes |
| **Input** | 77 engineered features from 25 sensor channels plus the calendar; 30 retained after selection |
| **Architectures** | Persistence, Ridge, Random Forest, LSTM, GRU, CNN-LSTM |
| **Selection** | Best validation MAE, then re-scored once on the held-out test block |
| **Artefacts** | `models/best_model.keras`, `models/preprocessor.joblib`, `models/selected_features.json` |

## Intended use

Short-horizon load forecasting for a single dwelling: anticipating the next 10 minutes of
appliance demand for scheduling, storage dispatch or anomaly detection.

**Out of scope.** This model is fitted to one house over one four-and-a-half-month window
(January–May 2016, Belgium). It is not a general household load model. Applying it to a
different dwelling, a different climate, or a season outside the training window without
retraining is not supported — the occupancy pattern it has learned is that specific household's.

Longer horizons are also out of scope as configured. `features.horizon` is a parameter and the
pipeline will run at 6 or 36 steps, but the accuracy reported here holds only at 1 step, and the
advantage over persistence is expected to decay quickly.

## Training data

- **Source:** Appliance Energy Prediction Dataset (UCI); Candanedo, Feldheim & Deramaix (2017).
- **Period:** 2016-01-11 17:00 to 2016-05-27 18:00, 10-minute resolution, 19,735 rows.
- **Quality:** no duplicate timestamps, no gaps in the 10-minute grid, no missing cells. Verified
  on every run by `energy-forecast validate` and recorded in the run manifest.
- **Excluded:** `rv1` and `rv2`, the source study's random noise columns, confirmed numerically
  identical to each other and uncorrelated with the target.
- **Warm-up:** the first 1,008 rows (seven days) are consumed by the weekly lag.

Each run records a SHA-256 of the raw file, so a result can always be tied to the exact data that
produced it.

## Evaluation

- **Protocol:** chronological split. First 72% train, next 8% validation, final 20% test. Never
  shuffled. No model, scaler, feature selector or hyper-parameter sees the test block.
- **Metrics:** MAE and RMSE in Wh (primary), with MAPE and R² alongside.
- **Baseline:** persistence (`ŷ[t] = y[t−1]`). At this horizon the lag-1 autocorrelation is ≈0.75,
  so persistence is a strong competitor and the honest reference point.

Current numbers live in `reports/metrics.json` and `reports/runs/latest.json`, generated by the
run rather than transcribed here.

## Limitations and known failure modes

1. **Error concentrates in the spikes.** Absolute error on quiet low-consumption periods is
   small; the large errors sit almost entirely in the high-consumption evening events — which are
   the periods most worth predicting. See the error-by-consumption-band table in the report.
2. **Single held-out block.** One estimate, not a distribution. Walk-forward validation across
   several folds would say how stable the result is.
3. **Point forecast only.** No uncertainty estimate. Given where the errors sit, a prediction
   interval would be more useful operationally than a sharper point estimate.
4. **Seasonal coverage.** Training spans winter into late spring. Summer behaviour — cooling load,
   longer daylight, holidays — is unobserved.
5. **Occupancy is only implied.** `lights` is a crude proxy; the model has no direct occupancy
   signal, which is likely why the spikes are hard.
6. **Heteroscedastic residuals.** Expected here, but it means a constant error bar would be
   misleading across consumption levels.

## Ethical and privacy considerations

The data is a behavioural trace of a private household: 10-minute energy readings reveal when
occupants wake, cook, leave and return. The published dataset is already anonymised and
consented, but anything derived from it inherits that sensitivity.

- Do not join these predictions to identifying information about occupants.
- Treat both raw data and predictions as personal data under GDPR if deployed on real households.
- Automated decisions that materially affect occupants (tariff changes, service restriction)
  should not be made from this model alone.

## Leakage controls

Temporal leakage is the dominant correctness risk for this class of model, so it is enforced
mechanically and verified by test:

| Control | Location |
|---|---|
| Exogenous sensors lagged, never contemporaneous | `features.FeatureBuilder._add_exogenous` |
| Rolling windows computed on an already-shifted series | `features.FeatureBuilder._add_rolling` |
| Every feature declares `min_lag`; a violation raises `LeakageError` at build time | `features.FeatureBuilder._record` |
| Scalers, winsorising fences and selector fitted on train only | `preprocessing`, `selection` |
| Chronological split | `splitting.chronological_split` |
| Windows end strictly before their target | `sequences.make_sequences` |

Verified by `tests/test_features_leakage.py`, whose central test corrupts all data after a cut
point and asserts no earlier feature changed, and by
`test_persistence_is_a_genuine_competitor`, which treats an implausibly large win over
persistence as a leakage alarm rather than a success.

## Reproducibility

Every run writes `reports/runs/<run_id>/manifest.json` containing the run id, git commit and
dirty flag, SHA-256 of the data, a digest and full copy of the config, library versions, the
selected features, and all metrics. `energy-forecast runs` compares them.

Seeds are set for Python, NumPy and TensorFlow from `project.random_state`. Exact
bit-reproducibility on GPU is not guaranteed — cuDNN kernel selection is non-deterministic unless
determinism is explicitly forced, at a performance cost.

## Maintenance

- **Retrain trigger:** monthly, or when the data quality report diverges from the manifest the
  deployed model recorded.
- **Monitoring:** compare live MAE against the persistence baseline computed on the same window.
  If the model stops beating persistence, it has stopped earning its complexity.
- **Rollback:** artefacts are versioned per run; redeploying is restoring an earlier
  `models/` directory and its manifest.
